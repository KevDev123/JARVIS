B03579 6. Ciclo de vida de un mensaje
B03580 Veamos qué ocurrirá cuando escribas:
B03581 «Jarvis, explícame qué es Firebase».
B03582 Validación
B03583 Se comprueba que el mensaje no esté vacío y que la conversación sea válida.
B03584 Persistencia inicial
B03585 Se guarda el mensaje del usuario y se registra la solicitud de generación.
B03586 Preparación de contexto
B03587 Se recuperan los mensajes pertinentes y se respetan los límites del modelo.
B03588 Solicitud al proveedor
B03589 El adaptador Ollama inicia la generación.
B03590 Streaming
B03591 Los fragmentos recibidos se muestran progresivamente.
B03592 Finalización
B03593 Se confirma el resultado y se guarda la respuesta con su estado.
B03594 Actualización visual
B03595 La interfaz muestra el estado final y habilita nuevas interacciones.
B03596 Si falla el guardado inicial, Jarvis no deberá presentar el mensaje como persistido.
B03597 Podremos decidir si permitir una conversación temporal en memoria, pero no será el comportamiento predeterminado del MVP.
B03598 7. Streaming: respuestas en tiempo real
B03599 El streaming permite mostrar una respuesta mientras el modelo la está generando.
B03600 No esperaremos necesariamente a recibir todo el texto.
B03601 Diseño propuesto
B03602 El adaptador recibirá fragmentos del proveedor.
B03603 El coordinador comprobará que pertenecen a una generación activa.
B03604 Después los entregará a la interfaz mediante eventos.
B03605 La interfaz acumulará el texto y lo actualizará de forma controlada.
B03606 No actualizaremos toda la ventana por cada carácter recibido.
B03607 Agruparemos actualizaciones cuando sea conveniente para evitar consumo excesivo de CPU.
B03608 Protección frente a respuestas tardías
B03609 Cada fragmento llevará asociado el identificador de generación.
B03610 Si el usuario cambia de conversación o cancela la respuesta, los fragmentos antiguos no podrán modificar otra conversación.
B03611 8. Cancelación segura
B03612 Cancelar una respuesta no es lo mismo que cerrar toda la aplicación.
B03613 Propongo tres niveles:
B03614 Cancelación de generación: detener la respuesta actual.
B03615 Cancelación de operación: detener una tarea interna concreta, como una comprobación de conexión.
B03616 Cierre de aplicación: detener trabajadores, guardar estados recuperables y liberar recursos propios.
B03617 Para el MVP, el caso principal será la cancelación de generación.
B03618 Flujo
B03619 El usuario presiona Detener.
B03620 Jarvis registra generation.cancel_requested.
B03621 El adaptador intenta interrumpir la solicitud.
B03622 El coordinador espera una confirmación o detecta la terminación real.
B03623 La generación termina como cancelada, completada o fallida, según corresponda.
B03624 El texto parcial podrá conservarse con una indicación clara de que está incompleto.
B03625 No se reutilizará automáticamente como respuesta final validada.
B03626 9. Persistencia y consistencia
B03627 SQLite será la fuente principal de verdad para las conversaciones guardadas.
B03628 Necesitaremos distinguir entre:
B03629 Estado visual: lo que aparece temporalmente en pantalla.
B03630 Estado de aplicación: la operación que está ocurriendo.
B03631 Estado persistido: lo que realmente quedó confirmado en SQLite.
B03632 Esta distinción evitará mensajes engañosos.
B03633 Reglas importantes
B03634 Una conversación no se considerará guardada hasta que la transacción correspondiente termine correctamente.
B03635 Los mensajes tendrán orden estable.
B03636 Las generaciones interrumpidas conservarán un estado explícito.
B03637 Al reiniciar Jarvis, las generaciones que quedaron activas por un cierre inesperado se marcarán como interrumpidas tras la recuperación.
B03638 No reenviaremos automáticamente solicitudes incompletas sin una decisión explícita.

B03643 Los errores internos tendrán identificadores de diagnóstico.
B03644 La interfaz no mostrará trazas completas de Python al usuario normal, pero podrá ofrecer información técnica redactada para diagnóstico.
B03645 No registraremos claves, tokens ni conversaciones completas en los logs técnicos por defecto.
B03646 11. Seguridad de los contratos
B03647 Aunque el MVP no ejecutará herramientas, estableceremos desde ahora reglas para impedir que un proveedor obtenga capacidades que no le corresponden.
B03648 El modelo produce contenido; no concede permisos.
B03649 Una respuesta como «ejecuta este comando» será tratada como texto.
B03650 El adaptador Ollama no tendrá funciones de ejecución de comandos, modificación de archivos o control de Windows.
B03651 Los contratos futuros de herramientas serán independientes y pasarán por el Security Gateway.
B03652 También evitaremos interpretar contenido generado como HTML activo o instrucciones ejecutables dentro de la interfaz.
B03653 12. Contratos de configuración
B03654 Las preferencias deberán validarse y persistirse de forma controlada.
B03655 Propongo separar:
B03656 Configuración de usuario: tema, inicio automático, modelo preferido y comportamiento de ventanas.
B03657 Configuración del proveedor: dirección local autorizada, tiempos de espera y parámetros compatibles.
B03658 Configuración interna: versión de esquema, límites operativos y opciones técnicas.
B03659 Los cambios críticos no se aplicarán silenciosamente si pueden interrumpir una generación activa.
B03660 Por ejemplo, cambiar de modelo mientras Ollama está respondiendo deberá esperar, cancelar la generación mediante confirmación o aplicarse únicamente a la siguiente solicitud.

B03690 J.A.R.V.I.S. — Plan Maestro de Validación y Aceptación
B03691 DISEÑO CONCEPTUAL · VERSIÓN 2.4 · MVP 0.1
B03692 Objetivo: establecer cómo comprobaremos que Jarvis funciona correctamente, es estable, protege la información y mantiene un consumo razonable de recursos antes de aprobar su primera versión.
B03693 Conservamos todas las decisiones anteriores: Python 3.12 + PySide6 + Ollama + SQLite, arquitectura modular eficiente, seguridad equilibrada y funcionamiento Local First + API Ready.

B03695 1. ¿Cuándo consideraremos terminado Jarvis 0.1?
B03696 No bastará con que Jarvis abra una ventana y responda una pregunta.

B03700 2. Estrategia de pruebas
B03701 Propongo cinco niveles de validación.
B03702 Nivel | Qué comprobaremos | Dependencia de Ollama
Unitarias | Reglas, estados, validaciones | No
Contratos | Interfaces y formatos de respuesta | No, con simulaciones
Integración | Core, SQLite y adaptador Ollama | Parcial
End-to-end | Flujo completo desde PySide6 | Sí
Aceptación | Uso real, rendimiento y recuperación | Sí
B03703 Este enfoque nos permitirá detectar muchos errores sin cargar un modelo local en cada prueba.
B03704 Por ejemplo, para comprobar la cancelación podremos utilizar un proveedor simulado que envíe fragmentos lentamente.
B03705 Después repetiremos la prueba con Ollama real para confirmar que la integración se comporta correctamente.
